02现象描述

2026-10-26 19:40–20:30 期间，TokenFlux 中转站 /v1/chat/completions 接口偶发返回 504 Gateway Timeout，并非全部请求失败，而是间歇性、按路由不均分布。Web 端（codex / claude 工作台）与直接 API 调用均受影响，用户侧表现为"请求卡住数秒后报上游超时"。

关键观察：错误集中在上游读取超时（read timed out），而非连接拒绝或鉴权失败，指向上游响应慢/排队，而非 DNS 或网络断开。

03复现步骤

该问题在高峰期偶发复现，触发条件为并发请求数超过上游连接池上限时。以下为可稳定触发的最小复现路径：

  1. 构造并发压测，同时发起 60+ 个 /v1/chat/completions 请求到 glm-5.3 路由。
  2. 上游连接池默认上限 50，超出部分排队等待连接。
  3. 单请求上游处理耗时 > 15s 时（高峰期排队），中转站 30s 读取超时触发。
  4. 命中超时阈值 → 返回 504。

05根因分析

通过指标时序与调用链交叉比对，定位为直接原因 + 深层原因两层叠加，非单点故障。

定位路径

[19:40] 错误率抬升 0.2% → 3.1%
[19:50] 定位到错误全部为 504 upstream_timeout
[19:55] 按路由拆分：仅 glm-5.3 / claude 上游抖动
[20:05] 查上游网关连接数：持续打满 50/50
[20:15] 确认中转站超时阈值 30s 过短，高峰期排队必超
[结论] 上游连接池耗尽 + 超时阈值过短 = 复合根因
直接原因：上游网关连接池上限 50，高峰期并发 >50 时新请求排队，单请求上游耗时长于中转站 30s 阈值。
深层原因：中转站未按"连接建立 vs 首字节 vs 完整读取"拆分超时，统一 30s；且无熔断/降级，连接池满时不快速失败而是阻塞排队，放大雪崩。

08遗留问题 / 下一步

  • 连接池上限应改为按上游动态可配置，并随流量自动扩缩，而非固定值。
  • 需补充熔断告警：连接池利用率持续 >90% 超过 2 分钟即触发钉钉/飞书告警。
  • 建议对 Web 工作台侧增加客户端指数退避重试，降低高峰期瞬时并发。
  • 后续需验证 claude 路由是否同样存在连接池瓶颈（本次仅 glm-5.3 峰值打满）。
